# ADR 004: Typed vector storage and representation separation

**Status:** Amended by [ADR-013](ADR-013.md) and [ADR-014](ADR-014.md), 2026-10-12; implementation verification pending [Epic 7.8](../epic7.8-open-ie-ontology-alignment.md).\
**Current contract:** [FOUNDATIONAL](../../FOUNDATIONAL.md).\
**Supersession:** ADR-013 records semantic corrections; ADR-014 selects the single implementation and all-gates handoff to Epics 8.x.

## Current decision

Retain direct vector storage and strict representation/dimension separation. Space S supplies entity candidates; space R ranks qualified facts and chunks against queries. Invalid dimensions fail explicitly. Vector similarity is not logical identity, and KB vectors are not a second similarity source.

The current contract and this summary govern. The original decision below is retained solely as history, including its original status and test claims; those claims are not evidence of Epic 7.8 completion.

# ADR 004: Strict Embedding Boundary & Direct Vector Projection

**Status:** Accepted (Remediated Architecture)\
**Date:** 2026-10-05 (Updated 2026-10-07)\
**Amended by:** [ADR-012](ADR-012.md) — the per-model "Strict Embedding Boundary" (Gemma for chunks, spaCy for everything else) is replaced by the three-space Representation-Space Contract (L = spaCy linguistics, S = Gemma sentence similarity for entity candidate generation, R = Gemma asymmetric retrieval for chunks + facts); `leaf_nodes.embedding` is dropped.\
**Governing Canon:** [`FOUNDATIONAL.md §2 (Invariant 3), §3, §4`](../../FOUNDATIONAL.md), [`docs/epics-alignment-roadmap.md §3`](../epics-alignment-roadmap.md)\
**Implementation:** [`src/yaw/storage/db.py`](../../src/yaw/storage/db.py), [`src/yaw/nlp/embeddings.py`](../../src/yaw/nlp/embeddings.py), [`src/yaw/indexer/canonicalize.py`](../../src/yaw/indexer/canonicalize.py), [`src/yaw/retrieval/retriever.py`](../../src/yaw/retrieval/retriever.py)

---

### Context & Problem Statement

Modern RAG and knowledge graph architectures frequently blur the boundary between document-level passage retrieval and symbolic concept resolution. In earlier iterations, external dense embedding calls (e.g., `embed-gemma-300m-FLM` via Ollama `/api/embed`) were invoked indiscriminately across document chunks, extracted entity mentions, and relational predicates.

This introduced severe architectural antipatterns:
1. **Embedding Model Mismatch:** Asymmetric dense document embedders (`embed-gemma-300m-FLM`) are trained on long text passages with prompt task prefixes (`"task: search result | query: "`). They are poorly calibrated for short lexical entity mentions (e.g., `"Einstein"` vs `"Albert Einstein"`) and verbal predicates.
2. **Excessive IPC & Latency Overhead:** Invoking external Ollama HTTP endpoints for every extracted entity and predicate during ingestion created massive network overhead, stalling indexing.
3. **Invariant 3 & Portability Hazards:** Offloading vector storage to external multi-container vector databases violates Invariant 3 (single in-process SQLite architecture).

### Decision

Codify the **Representation-Space Contract** (originally the "Strict Embedding Boundary Contract"; reworded per job by [ADR-012 §1](ADR-012.md)) and **Direct SQLite BLOB Storage with `sqlite-vec` Projection**:

| Space | Representation | Job | Stores |
| :--- | :--- | :--- | :--- |
| **L: Linguistic** | In-process spaCy `en_core_web_lg` (lemmatizer, parser, NER, polarity mask; static 300d vectors only as the guarded last predicate tier) + `InMemoryLookupKB` (alias → candidate prior index) | Predicate canonicalization, Tier 1 normalized keys, Tier 2 corroboration, query mentions | In-process only |
| **S: Symmetric similarity** | `embed-gemma-300m-FLM`, `task: sentence similarity \| query: {name}: {definition}` | Entity-identity candidate generation (Tier 2 blocking) | `entity_vec` (`vec0`) |
| **R: Asymmetric retrieval** | `embed-gemma-300m-FLM`, documents `title: {note_title \| none} \| text: {content}`, queries `task: search result \| query: {query}` | Query → chunk and query → fact relevance; in-memory bi-encoder reranking | `note_chunks.embedding`, `fact_vec` (`vec0`) |

1. **Representation-Space Contract ([ADR-012 §1](ADR-012.md)):**
   - **Space R (Chunks, Facts & Retrieval Queries):** `embed-gemma-300m-FLM` asymmetric retrieval embeds note chunks (`note_chunks.embedding`), rendered facts (`fact_vec`) and search queries. Documents are formatted with `title: {note_title | none} | text: {content}`, and queries with `task: search result | query: {query}`.
   - **Space S (Entity Identity Candidates):** one `embed-gemma-300m-FLM` embedding with the `task: sentence similarity` prompt per **new** canonical entity, stored in `entity_vec` and used only for Tier 2 blocking, never for retrieval.
   - **Space L (Lexical Operations & Predicates):** predicate canonicalization, Tier 1 normalization and Tier 2 corroboration belong to the in-process spaCy pipeline. Static 300d vectors are used only as the polarity-guarded last tier onto the base predicates. `InMemoryLookupKB` is never a similarity source.
   - **Zero Gemma Calls for Predicates:** predicates trigger zero embedding requests. A similarity is computed only between two vectors of the same space.
2. **Binary Float32 BLOB Storage:**
   - Vector embeddings are serialized to raw compact IEEE 754 float32 byte buffers (`arr.astype(np.float32).tobytes()`, exactly 3,072 bytes per 768-d vector) via `yaw.nlp.serialize_embedding()`.
   - Stored directly in the `note_chunks.embedding` BLOB column; new vector stores (`entity_vec`, `fact_vec`) are `sqlite-vec` `vec0` tables that reject dimension-mismatched inserts ([ADR-012](ADR-012.md)). `leaf_nodes` has no vector column.
3. **In-Process `sqlite-vec` Cosine Projection:**
   - The `sqlite-vec` C extension is dynamically loaded on connection initialization (`yaw.storage.load_vec_extension(conn)`).
   - Distance queries execute in SQL:
     ```sql
     SELECT chunk_id, vec_distance_cosine(embedding, ?) AS distance
     FROM note_chunks
     ORDER BY distance ASC
     LIMIT ?
     ```
     Cosine similarity is derived directly as $\text{sim} = \max(0.0, 1.0 - \text{distance})$.
4. **ARCH-PERF-002: In-Memory Bi-Encoder Candidate Rescoring:**
   - Candidate reranking in [`rerank_candidates()`](../../src/yaw/nlp/embeddings.py) uses NumPy dot-product cosine projection over in-memory vectors.
   - Zero outbound HTTP requests occur during candidate rescoring.

### Consequences & Trade-offs

- **Positive:** Bounded external HTTP embedding calls during canonicalization: zero for predicates, one batched space-S call per **new** canonical entity ([ADR-012](ADR-012.md) cost model).
- **Positive:** Strictly upholds Invariant 3: 100% self-contained in a single `yaw.db` file with zero external database daemons or client-server bridges.
- **Positive:** Clear architectural separation: one representation space per job and per vector store (L linguistic, S entity similarity, R retrieval).
- **Positive:** Zero serialization overhead: direct BLOB storage eliminates JSON array parsing bottlenecks.
- **Trade-off:** `en_core_web_lg` model artifacts (~560 MB) must be present in the local environment for the space-L pipeline and its static 300d predicate fallback vectors (with automatic fallback to `md`/`sm` if absent).
