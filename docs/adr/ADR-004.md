### Context & Problem Statement

Modern RAG and knowledge graph architectures frequently blur the boundary between document-level passage retrieval and symbolic concept resolution. In earlier iterations, external dense embedding calls (e.g., `embed-gemma-300m-FLM` via Ollama `/api/embed`) were invoked indiscriminately across document chunks, extracted entity mentions, and relational predicates.

This introduced severe architectural antipatterns:
1. **Embedding Model Mismatch:** Asymmetric dense document embedders (`embed-gemma-300m-FLM`) are trained on long text passages with prompt task prefixes (`"task: search result | query: "`). They are poorly calibrated for short lexical entity mentions (e.g., `"Einstein"` vs `"Albert Einstein"`) and verbal predicates.
2. **Excessive IPC & Latency Overhead:** Invoking external Ollama HTTP endpoints for every extracted entity and predicate during ingestion created massive network overhead, stalling indexing.
3. **Invariant 3 & Portability Hazards:** Offloading vector storage to external multi-container vector databases violates Invariant 3 (single in-process SQLite architecture).

### Decision

Codify the **Strict Embedding Boundary Contract** and **Direct SQLite BLOB Storage with `sqlite-vec` Projection**:

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                               STRICT EMBEDDING BOUNDARY                                │
├───────────────────────────────────────────┬────────────────────────────────────────────┤
│   Document Chunks & Retrieval Queries     │    Entity Mentions & Relational Triples    │
│  (embed-gemma-300m-FLM via Ollama /embed) │      (100% In-Process spaCy en_core_web_lg)│
├───────────────────────────────────────────┼────────────────────────────────────────────┤
│ • note_chunks.embedding (Float32 BLOB)    │ • leaf_nodes / leaf_relations tokens       │
│ • s_chunks_vec (query embedding)          │ • Static 300d GloVe vectors (nlp.vocab)    │
│ • In-memory bi-encoder reranking          │ • InMemoryLookupKB candidate generation    │
│ • Task prefixes: "task: search result..." │ • Zero external Gemma HTTP calls           │
└───────────────────────────────────────────┴────────────────────────────────────────────┘
```

1. **Strict Embedding Boundary Contract:**
   - **Long Document Chunk Indexing & Retrieval Queries:** `embed-gemma-300m-FLM` is strictly restricted to long document chunk indexing (`note_chunks.embedding`) and search retrieval queries (`s_chunks_vec`). Chunks are formatted with `title: {doc_title} | text: {content}`, and queries are formatted with `task: search result | query: {query}`.
   - **Post-Indexing Lexical Operations & Canonicalization:** All post-indexing lexical operations, concept canonicalization (Two-Tier Convergence Engine), and $(s, p, o)$ triplet treatments belong **100% to the in-process spaCy pipeline** (`en_core_web_lg` static 300d GloVe vectors, `InMemoryLookupKB`, and token cosine similarity).
   - **Zero External Gemma Calls for Entities or Predicates:** No external embedding requests are ever made to Ollama for extracted entities or relation phrases.
2. **Binary Float32 BLOB Storage:**
   - Vector embeddings are serialized to raw compact IEEE 754 float32 byte buffers (`arr.astype(np.float32).tobytes()`, exactly 3,072 bytes per 768-d vector) via `yaw.nlp.serialize_embedding()`.
   - Stored directly in `embedding BLOB` columns in SQLite (`note_chunks.embedding` and optional `leaf_nodes.embedding`).
3. **In-Process `sqlite-vec` Cosine Projection:**
   - The `sqlite-vec` C extension is dynamically loaded on connection initialization (`yaw.storage.load_vec_extension(conn)`).
   - Distance queries execute in SQL:
     ```sql
     SELECT chunk_id, vec_distance_cosine(embedding, ?) AS distance
     FROM note_chunks
     ORDER BY distance ASC
     LIMIT ?
     ```
     Cosine similarity is derived directly as $\text{sim} = \max(0.0, 1.0 - \text{distance})$.
4. **ARCH-PERF-002: In-Memory Bi-Encoder Candidate Rescoring:**
   - Candidate reranking in [`rerank_candidates()`](file:///home/harri/yaw/src/yaw/nlp/embeddings.py) uses NumPy dot-product cosine projection over in-memory vectors.
   - Zero outbound HTTP requests occur during candidate rescoring.

### Consequences & Trade-offs

- **Positive:** Complete elimination of external HTTP embedding calls during entity extraction and canonicalization, drastically speeding up ingestion.
- **Positive:** Strictly upholds Invariant 3: 100% self-contained in a single `yaw.db` file with zero external database daemons or client-server bridges.
- **Positive:** Clear architectural separation: dense semantic embeddings for passages, static distributional vectors for symbolic graph nodes.
- **Positive:** Zero serialization overhead: direct BLOB storage eliminates JSON array parsing bottlenecks.
- **Trade-off:** `en_core_web_lg` model artifacts (~560 MB) must be present in the local environment for static 300d vectors (with automatic fallback to `md`/`sm` if absent).
