# ADR 014: One evidence-preserving corpus compiler before Epic 8

**Status:** Accepted implementation direction, 2026-10-12; runtime verification pending.\
**Authority:** Owner's clarification: 100–500 documents, mainly English with occasional other languages; quality over prescribed patterns; one functioning path with zero fallbacks before Epics 8.x.\
**Contract:** [FOUNDATIONAL](../../FOUNDATIONAL.md).\
**Execution:** [Epic 7.8](../epic7.8-open-ie-ontology-alignment.md); [compiler guide](../knowledge-compilation.md).

## Decision and rationale

Retain CocoIndex, spaCy/spacy-llm, Ollama, SQLite, RDFLib/pySHACL and SciPy. The missing capability is the complete lifecycle from source claims to maintained cross-document knowledge. There is no demonstrated library limitation justifying a DSPy migration. spaCy-llm already provides public task, parser, model and cache interfaces; use these without private patches. [spaCy-llm](https://spacy.io/api/large-language-models).

Select one CocoIndex application containing source processing and a shared corpus compilation component. Its explicit input manifest determines derived work. There is no alternate post-sync compiler, manual-only compilation architecture or second indexing system. CocoIndex supports shared processing components and cross-file graph work; the selected pinned runtime must prove YAW's lifecycle and publication requirements in Epic 7.8. If it cannot, that gate remains blocked until this decision is explicitly replaced. Do not implement a fallback. [Components](https://cocoindex.io/docs/programming_guide/processing_component/), [cross-file example](https://cocoindex.io/docs/examples/meeting-notes-to-knowledge-graph/).

Use `spacy.Raw.v1` with one shared Ollama adapter and validated task-specific payloads. Extraction, claim comparison and wiki authoring are distinct planned responsibilities in that application, not competing extractors or recovery attempts. The extraction task emits source claims; compilation creates labelled interpretations and synthesis. No generative identity adjudication, automatic model substitution or second parser is selected. The [spaCy guide](../how-to-handle-spacy-llm.md) fixes the component recipe.

Treat source assertions, interpretations, admitted logical facts and generated organization as distinct records. Preserve disagreement, revisions, attribution and uncertainty. Similarity, an LLM explanation, a SHACL pass and a high graph score do not establish truth. OWL's open-world semantics and SHACL's graph validation require an explicit claim/admission model. [OWL](https://www.w3.org/TR/owl2-primer/), [SHACL](https://www.w3.org/TR/shacl/).

For this corpus size, cache unchanged extraction and generated outputs, and recompute deterministic corpus projections from the active manifest. This is the selected initial strategy; measure total tokens, assertions, graph size, calls and memory before replacing it with more complicated incremental graph algorithms. No ingestion-time SLA has been agreed.

## Exact amendments

This ADR amends ADR-013 and the current summaries of earlier ADRs where listed. Historical bodies are evidence of previous decisions only.

| Earlier provision | Selected replacement |
| --- | --- |
| Raw task **or** equivalent custom extractor; mandatory five-task and REL recipes | Raw task plus one typed parser/grounding adapter; remove competing production paths |
| Preferred shared compiler **or** post-sync fallback | One shared CocoIndex corpus component; an unsupported pinned runtime blocks completion |
| One generation as a total compilation budget | One extraction request per changed extraction unit, followed by explicitly scheduled comparison and synthesis work; cache and measure each responsibility |
| Optional use of every spaCy capability | The fixed linguistic/candidate recipe in the spaCy guide; additional components require evidence and replacement of the selected recipe |
| No generative identity adjudication | Retained: comparison and synthesis cannot create accepted identity bindings or `owl:sameAs` |
| Optional hierarchy/core compilation first delivered in Epic 8.1 | Corpus compilation, organizational hierarchy and stored synthesis function before Epic 7.8 closes; export remains an optional output |
| Nine roots or fewer-than-ten umbrella concepts as semantic truth | Nine umbrella groups is an organization target; unsupported grouping remains unperformed and the unmet target is reported |
| Several closure engines / validation-only compilation | One pySHACL-based enrichment and validation sequence, with an explicit supported profile and conservative derivation provenance |
| Offline embeddings, heuristic parsing, legacy scorers or live-lint escape paths | Explicit typed errors; legitimate empty data is handled by the same algorithm; lint reads the compiler's findings |
| Fixed latency and hierarchy superiority claims | Measured costs and independently labelled quality checks; selected parameters are versioned, not asserted to be optimal |
| Applicable 7.8 gates suffice to begin 8.x | All 7.8 gates, including retained 7.7 work and an actual-model pilot, must pass before any Epic 8 implementation starts |

The earlier logarithmic conductance proposal becomes the single starting scorer policy in the [PPR guide](../power-pagerank.md). Alternatives exist only in offline evaluation, never as runtime recovery or automatically selected modes. Evidence may justify a future replacement through an explicit amended decision and migration.

## Consequences and verification

More complete claim metadata and dependency tracking are required. The design deliberately avoids a separate graph service, a second LLM framework and a second semantic engine. This is a bounded engineering target, not a promise to infer every contradiction or ontology axiom from arbitrary prose.

Epic 7.8 must demonstrate ingestion, cross-document interpretation, enrichment, validation, synthesis, query/lint, edit/deletion propagation and explicit failures through the same deployed path. Epics 8.1–8.3 then harden, evaluate and package that functioning engine. [Acceptance scenarios](../USER_STORIES.md) define observable obligations; [TEST_READY](../../TEST_READY.md) records actual evidence.
