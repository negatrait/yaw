### Context & Problem Statement

YAW requires robust HTTP communication for Ollama LLM extraction, embedding generation, and FastMCP server-client transport.
Testing these network boundaries presents a classic dilemma:
1. **Flaky External Dependencies:** Testing against live external daemons (e.g., a real Ollama instance or internet endpoint) introduces non-deterministic test failures, latency spikes, and CI failures in sandboxed or offline build pipelines.
2. **Tautological Mocking (`unittest.mock`):** Mocking HTTP client libraries (`requests`, `httpx`, `urllib.request`) replaces real network behavior with synthetic fixtures. Tautological mocks fail to exercise genuine socket I/O, OS buffer limits, TCP connection teardown, HTTP status code framing, or byte serialization quirks.

### Decision

Adopt **In-Process Loopback HTTP Isolation** via Standard Library `http.server.HTTPServer`:
1. **Dynamic Ephemeral Port Binding:**
   The test suite binds a lightweight HTTP server to `127.0.0.1:0`. The OS kernel dynamically assigns an available ephemeral port, eliminating port collision risks during parallel test runs (`pytest -n auto`).
2. **Daemon Thread Execution & Graceful Teardown:**
   The server runs in a background daemon thread managed by a pytest fixture:
   ```python
   @pytest.fixture
   def loopback_server():
       server = HTTPServer(("127.0.0.1", 0), _LoopbackHandler)
       port = server.server_port
       thread = threading.Thread(target=server.serve_forever, daemon=True)
       thread.start()
       yield f"http://127.0.0.1:{port}"
       server.shutdown()
   ```
3. **Real Socket & Wire Protocol Exercise:**
   Application configuration endpoints (`config.OLLAMA_HOST`, `config.HOST`) are pointed to the loopback URL. HTTP requests travel through real OS network stacks, serializing real bytes, validating JSON schemas, and triggering real connection timeouts.
4. **Hermetic Sandbox Conformance:**
   Zero external internet egress is required. Test execution complies fully with strict sandbox environments while verifying real network invariants without mocking.

### Consequences & Trade-offs

- **Positive:** Strictly upholds Invariant 6 (Real-Invariant Testing, zero tautological cushion mocks).
- **Positive:** 100% deterministic and offline-capable: runs reliably in CI sandboxes without outbound network access.
- **Positive:** Validates end-to-end HTTP serialization, headers, status codes, and error handlers across real sockets.
- **Trade-off:** In-process servers consume modest thread resources and require careful fixture cleanup (`server.shutdown()`) to avoid thread leaks.
